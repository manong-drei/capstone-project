# Admin audit logs

Before deploying the updated server, run `npm run migrate:audit` from `server/` using the deployment database configuration. The migration creates `audit_logs` and its indexes; rerunning it is safe. If the original schema's unused `audit_logs` table exists (with `log_id`, `user_id`, `table_name`, and `record_id`), it is preserved intact as `audit_logs_legacy` before creating the new table. The migration refuses to overwrite an existing legacy archive or an unrecognized schema. It does not import or delete history, or change existing patient/password audit tables. Back up the database using the normal deployment process.

The admin dashboard's **Audit Logs** tab reads `GET /api/admin/audit-logs`. Supported filters are `page` (default 1), `limit` (default 20, maximum 100), `dateFrom`, `dateTo` (inclusive Philippine calendar dates, `YYYY-MM-DD`), `actor` (literal name search or exact ID), `actorRole` (`admin` or `staff`), `action`, and `outcome` (`success`, `failed`, `denied`). With no role filter, the feed includes all retained events, including patient SMS recovery. Results contain `events` and `pagination`. UTC timestamps are serialized with `Z` and displayed in Philippine time.

The feed includes account creation, deactivation and reactivation, registered mobile number changes, temporary password issuance and replacement, completed and failed SMS recovery, patient merges and duplicate overrides, individual ticket cancellations, bulk holds, SMS threshold changes, admin sign-ins, and access denials. Routine profile edits, record views, individual holds, and other routine queue and appointment activity stay in their source records or existing patient audit history where applicable.

Successful audited mutations and their audit rows commit or roll back together. Rejected requests for retained actions and access denials are recorded separately after the response finishes. Sign-in auditing is best effort and logs a fixed error message if unavailable. Monitor server output for `Audit recording failed.` and `Patient access audit recording failed.` before relying on history completeness.

Staff events cover patient account creation, temporary password issuance, registered mobile number changes, patient merges, and duplicate warning overrides. Individual ticket cancellations record the ticket ID for staff or administrator actions. A staff bulk hold records one event with the count of tickets held, and an empty hold produces no event. New coverage starts at deployment and uses the existing audit schema.

Denied requests against admin routes can identify another role or an unauthenticated visitor. Failed sign-ins targeting a known administrator identify the target account. Development sessions are labeled explicitly. IP addresses use Express's existing direct-connection policy.

Patient SMS recovery writes `password.recovery_completed` and `password.recovery_failed`. Completion identifies the verified patient. Failed attempts use an unauthenticated actor and include the targeted patient in the details. Recovery details include the shared recovery ID, patient name/ID, masked phone, controlled status/reason and SMS method. These events commit with the recovery state or password change. The SMS worker reconciles expiry and delivery failures. In-person recovery by staff or administrators records `password.issued` and, when applicable, `account.phone_changed`. See `ACCOUNT_RECOVERY.md`.

Logs can contain active-state and threshold changes, masked phone suffixes, record identifiers, and controlled account deactivation reasons. Free-text cancellation reasons stay on the source ticket. Passwords, hashes, tokens, medical content, verification answers, and raw request/response bodies are excluded. Older audit rows remain in storage.

The application exposes no write/update/delete audit endpoints, no history export, and no automatic retention deletion. Database operators must restrict table access and maintain backups using existing operational controls. Existing roles and account permissions are unchanged.
