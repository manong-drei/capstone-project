# Admin audit logs

Before deploying the updated server, run `npm run migrate:audit` from `server/` using the deployment database configuration. The migration creates `audit_logs` and its indexes; rerunning it is safe. If the original schema's unused `audit_logs` table exists (with `log_id`, `user_id`, `table_name`, and `record_id`), it is preserved intact as `audit_logs_legacy` before creating the new table. The migration refuses to overwrite an existing legacy archive or an unrecognized schema. It does not import or delete history, or change existing patient/password audit tables. Back up the database using the normal deployment process.

The admin dashboard's **Audit Logs** tab reads `GET /api/admin/audit-logs`. Supported filters are `page` (default 1), `limit` (default 20, maximum 100), `dateFrom`, `dateTo` (inclusive Philippine calendar dates, `YYYY-MM-DD`), `actor` (literal name search or exact ID), `action`, and `outcome` (`success`, `failed`, `denied`). Results contain `events` and `pagination`. UTC timestamps are serialized with `Z` and displayed in Philippine time.

The feed and its pagination include account creation, deactivation and reactivation, temporary password issuance and replacement, completed and failed SMS recovery, patient merges and duplicate overrides, SMS threshold changes, admin sign-ins, and access denials. Older rows for other actions remain in storage and are excluded from the feed. Routine profile edits, record views, queue and appointment activity, and leave decisions stay in their source records or existing patient audit history where applicable.

Successful audited mutations and their audit rows commit or roll back together. Rejected requests for retained actions and access denials are recorded separately after the response finishes. Sign-in auditing is best effort and logs a fixed error message if unavailable. Monitor server output for `Audit recording failed.` and `Patient access audit recording failed.` before relying on history completeness.

Only verified administrators produce normal activity records. Denied requests against admin routes can identify another role or an unauthenticated visitor. Failed sign-ins targeting a known administrator identify the target account, never an authenticated actor. Development sessions are labeled explicitly. IP addresses use Express's existing direct-connection policy; this feature does not enable trust of forwarded IP headers.

Patient SMS recovery writes `password.recovery_completed` and `password.recovery_failed`. Completion identifies the verified patient. Failed attempts use an unauthenticated actor and include the targeted patient in the details. Recovery details include the shared recovery ID, patient name/ID, masked phone, controlled status/reason and SMS method. These events commit with the recovery state or password change. The SMS worker still reconciles expiry and delivery failures. Admin-assisted in-person temporary password issuance appears as `password.issued` with the in-person method. See `ACCOUNT_RECOVERY.md`.

Logs can contain active-state and threshold changes, masked phone suffixes, record identifiers, and controlled account deactivation reasons. Passwords, hashes, tokens, medical content, verification answers, and raw request/response bodies are excluded. Existing legacy audit tables retain their existing behavior and access restrictions.

The application exposes no write/update/delete audit endpoints, no history export, and no automatic retention deletion. Database operators must restrict table access and maintain backups using existing operational controls. Existing roles and account permissions are unchanged.
